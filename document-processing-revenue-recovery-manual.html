1 Purpose & the Big Picture

This manual explains how a document — an invoice, a claim, a permit, a title report, anything — moves through TSM's shared intake pipeline from the moment it's uploaded to the moment it becomes a routed, actionable, dollars-and-cents next step.

The pipeline is a single shared entry point (html/tsm-doc-search-multi.html) that every one of the nine verticals in Section 5 feeds through. A document doesn't get a different upload experience per client vertical — it gets classified once, against a shared AI router, and then handed to the vertical's own War Room → Strategist → Executive Portal relay chain.

Two other groups of verticals exist outside that chain, and this manual is explicit about the difference rather than blurring it: Appendix A covers verticals that are indexed in the shared search UI but not yet wired into the AI classifier, and Appendix B covers verticals with their own real relay chains that don't touch this shared pipeline at all.

A parallel, read-only view sits above all of this: html/sentinel-center.html polls the same TSM_<VERTICAL>_STRATEGIST_RELAY keys each vertical's Strategist stage writes and rolls them into a single cross-vertical risk board. It doesn't change how a document is processed — it's downstream of the relay chain, not part of it — but Section 5's per-vertical relay tables note which Sentinel key each Strategist stage feeds, since that's the same write a Strategist reviewer is already producing.

2 The Universal Intake Pipeline

Every document follows the same four-stage path, regardless of vertical:

StageFile Path
1. Upload / Intakehtml/tsm-doc-search-multi.html
2. AI Classificationserver.js — POST route using DOC_ROUTER_PROMPT / DOC_ROUTER_NODES
3. Vertical War Roomone page per vertical, e.g. html/war-rooms/re-war/re-war-room.html
4. Strategist → Executive Portalthe vertical's own relay chain (see Section 5)

The classifier's job is narrow and specific: given a filename and document content, return which vertical(s) a document belongs to, a document type, and a small set of structured fields (see Section 3). It does not decide what to do with the document — that's the War Room reviewer's job, informed by the fields the classifier extracted.

3 What Gets Captured From Every Document

Regardless of vertical, every intake record carries the same core field set. Knowing these fields matters because they're what a War Room reviewer sees on the document card, and what downstream routing logic (see Section 7) keys off of.

FieldWhat It Is
fileNamethe uploaded file's name
documentTypee.g. INVOICE, CLAIM, PERMIT, DENIAL, ESCALATION
vendorcounterparty name, when applicable
invoiceNothe document's own reference/claim/invoice number
exclusionCodea short code the classifier assigns — drives routing logic
amountdollar exposure, 0 if not applicable
sourceNode / routingwhich War Room node it lands on, and its relay path

A document can be tagged to more than one vertical at once (e.g. a 1003 loan application tags both Real Estate and FinOps) — in that case it's indexed once but routed into each relevant vertical's own chain independently.

4 The Mission Preview Checkpoint

Not every classification is trusted automatically. The system defines a confidence threshold (MISSION_PREVIEW_CONFIDENCE_THRESHOLD = 0.6 in the current codebase) — below that, or on any schema-validation failure, the document pauses in a Mission Preview modal for a human to confirm or correct the classification before it auto-routes.

This is a deliberate speed/safety trade-off: a confident, schema-valid classification skips the modal entirely so the common case stays fast, while a low-confidence or invalid one stops and asks rather than silently guessing.

Reviewer Note If you see a Mission Preview modal, that's the system telling you it isn't sure — don't rubber-stamp it. Check the extracted fields (documentType, exclusionCode, amount) against the actual document before confirming.

6 Document Card Controls (Every Vertical)

Every document card in the War Room carries the same baseline controls: an "Open Node" action that routes the reviewer into the vertical's War Room page pre-loaded with that document's context, and the core field set from Section 3 displayed on the card face (exclusion code, amount, routing path).

A populated exclusion code or a non-empty defectFlags array (used in Real Estate and Healthcare, see Section 5) should be read as a hold, not a suggestion — those fields exist specifically so a reviewer doesn't have to open the full document to know something needs attention.

7 Known Risk: Exclusion-Code Collisions

This is a real, code-documented routing risk — not a hypothetical. TSM's routing logic checks certain exclusion-code prefixes in a fixed order, and a code that happens to match the wrong prefix can misroute a document to the wrong recovery path.

Healthcare example (PA- prefix)

The router checks any exclusionCode starting PA- for an authorization block before it checks documentType for DENIAL. A real proof-pack demo document labels its denial code "PA-17" — if the live classifier reused that code verbatim, the appeal packet would misroute to prior-auth verification steps instead of the appeal steps it actually needs. The seeded demo version pins the code to "CO-50" (a real CARC-style denial code) specifically to avoid this collision.

Construction example (CO- prefix)

Similarly, a change-order document labeled "CO-017" would trip DENIAL_RISK routing if reused as its exclusion code — not the sharpest fit for a cost-variance dispute with an unresolved authorization question. The seeded demo version pins the code to "VAR-CO17" instead, which correctly routes to DOCUMENTATION_BLOCK (identify defects, send query, block release until resolved).

Why This Matters If you're hand-keying an exclusion code, or reviewing one an AI classifier assigned, treat "PA-", "CO-", "OA-", and "PR-" prefixes as reserved — they carry routing meaning beyond just being a reference number.

8 Quick-Reference Checklist — Don't Miss These

  • Check the exclusion code before trusting the routing — see Section 7's PA-/CO- collision risk.
  • A Mission Preview modal means low confidence — verify the fields, don't rubber-stamp it.
  • A populated defectFlags array (Real Estate, Healthcare) is a hold, not informational text.
  • BPO's Strategist stage is a real, built page (bpo-strategist.html) — a BPO item does get a Strategist hop, same as other verticals; see BPO_Client_Chain_Manual.docx for the full stage-by-stage steps.
  • RCM-OS and Property Accounting — Revenue Cycle are searchable but not classifier-routed — a document won't land there automatically (Appendix A).
  • Mortgage, Schools, HotelOps/Concierge, Honeywell, L1 Ticket, Logistics, and Supplier/Vendor sit entirely outside this pipeline (Appendix B) — don't look for them in doc-search.
  • Sentinel Center (html/sentinel-center.html) rolls up 8 of the 9 pipeline verticals — every one but NOC — plus Mortgage, Schools, HotelOps, and Concierge from Appendix B; check Section 5's Sentinel Center Feed rows for the exact relay key.
